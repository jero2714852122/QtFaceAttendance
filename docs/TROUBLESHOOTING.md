# 踩坑记录与排错手册

这份文档记录的是这个项目从零做到现在，实际遇到过的每一个问题：环境、界面、摄像头、
人脸识别、网络、数据库、构建与打包。写它的目的是**项目做完之后你想再复现一遍时，
不用再踩同样的坑**，也让面试被追问"你遇到过什么问题"时有话可说。

每条按四段写：

- **现象**：你看到的是什么
- **原因**：为什么会这样
- **处理**：怎么修
- **预防**：以后怎么不踩

标注了 **[已实测]** 的是我当场验证过的；标 **[推断]** 的是逻辑上确定、但没能在本机
复现的（比如需要拔掉内置摄像头）。没标注的默认是实测过。

## 先记住这个排错套路

遇到问题先按这四步走，能省掉一大半时间：

1. **程序不崩但没反应** → 看 Qt Creator 底部的"应用程序输出"面板。Qt 大量问题
   只发警告不报错，功能会静默失效。
2. **代码改了没生效** → 先确认跑的是哪个 exe。这个项目里 `build/Debug/` 是早期
   遗留的旧产物，真正在用的是 `build/Qt_6_9_1_msvc2022_64/Debug/`。
3. **画面不对** → 先想颜色通道（BGR 还是 RGB）和坐标系（镜像了没有），
   再怀疑算法。
4. **识别忽好忽坏** → 先分清是哪个阈值在起作用：检测阈值管"是不是脸"，
   识别阈值管"是不是同一个人"。

## 一、环境与工具

### 1.1 调试器起不来，F5 报错

- **现象**：Qt Creator 里按 F5 调试，报调试器相关的错误，或者断点根本不停。
- **原因**：Qt Creator 的版本和调试器扩展不匹配。MSVC 编译出来的程序不能配
  MinGW 那套调试器，需要 Windows SDK 里的 CDB。
- **处理**：升级 Qt Creator 到 20.0.1，装对应版本的 CDB 扩展，然后在套件里把
  调试器指向 `C:/Program Files (x86)/Windows Kits/10/Debuggers/x64/cdb.exe`。
- **预防**：装 Qt 的时候把对应版本的调试器一起装；换了 Qt Creator 版本，
  调试器扩展也要跟着换。

### 1.2 开了 MinGW 的套件，编译或运行行为不对

- **现象**：同一个项目换个套件打开，编译失败或者跑起来行为不一样。
- **原因**：这台机器上同时装了 MSVC 和 MinGW 两套 Qt。项目从头到尾用的是
  `Qt 6.9.1 (msvc2022_64)`，用 MinGW 打开会连不上 OpenCV 的 MSVC 库。
- **处理**：只留 MSVC 的套件给这个项目用。
- **预防**：一个项目从头到尾锁定一个套件，不要中途换。

### 1.3 改了代码，程序行为没变

- **现象**：源码明明改了，重新运行还是老样子。
- **原因**：跑到了旧的 exe。这个项目里同时存在过 `build/Debug/` 和
  `build/Qt_6_9_1_msvc2022_64/Debug/` 两个输出目录。
- **处理**：认准 `build/Qt_6_9_1_msvc2022_64/Debug/`，对比 exe 和源码的修改时间。
- **预防**：不要手工在别的目录建构建产物；旧的构建目录直接删掉。

### 1.4 OpenCV 的 DLL 找不到 / Debug 和 Release 混用

- **现象**：程序启动报缺少 `opencv_world4120.dll`，或者加载了却崩溃。
- **原因**：OpenCV 是动态库，DLL 必须和 exe 放在一起；而且 Debug 版叫
  `opencv_world4120d.dll`（带 d），Release 版叫 `opencv_world4120.dll`，
  两者不能混。
- **处理**：CMake 里加 POST_BUILD，用 `$<TARGET_FILE:opencv_world>` 自动复制，
  它会按当前构建配置挑对的那个。
- **预防**：永远不要让 DLL 复制变成手工步骤。

## 二、界面与布局

### 2.1 两个按钮挤在左边，不横排

- **现象**：加了 `QHBoxLayout`，按钮还是不在一行，挤在角落或者和别的控件重叠。
- **原因**：创建了布局、也往里面加了控件，但**从没把这个布局挂到父布局上**。
  一个没有父级的布局是"孤儿"，它记着自己的内容，却没有任何人向它要尺寸，
  里面的控件等于没被管理。
- **处理**：在往布局里加完控件之后补一句 `parentLayout->addLayout(childLayout);`。
- **预防**：区分两种写法，它们意思完全不同：
  - `new QHBoxLayout(某个控件)` 是把布局**装到控件上**，会顶掉这个控件原有的布局；
  - `某个布局->addLayout(子布局)` 才是嵌套布局该用的写法。

### 2.2 界面上出现一块说不清来源的空白

- **现象**：两个控件之间多出一条缝，找不到是谁占的位置。
- **原因**：同一个控件被 `addWidget` 了两次。布局把它当成两个条目，各留一份
  空间，控件最终只按后一个条目的位置摆放，前面那块就成了没主人的空白。
- **处理**：删掉重复的那次 `addWidget`。
- **预防**：布局代码写完扫一眼，同一个控件名不该出现两次。

### 2.3 点了列表里的一行，什么都没发生（本项目最典型的一个）

- **现象**：程序不崩、不报错，点列表行按钮不变亮、输入框不回填，功能完全静默。
- **原因**：`QObject::connect` 的发送者传进去的是**空指针**。连接那段代码写在
  控件创建之前，`employeeList_` 那一刻还是 `nullptr`。Qt 在运行期发现了，但只打印
  一条警告，不抛异常也不崩。
- **处理**：把连接代码挪到控件创建之后。
- **预防**：
  - 构造函数按"**先造控件 → 再连信号 → 最后装布局**"分三段写，不要交叉；
  - 遇到"点了没反应但不崩"，第一件事是看应用程序输出面板里的
    `invalid nullptr parameter`。

### 2.4 列表项的数据靠解析显示文字来取

- **现象**：本来能跑，某天把列表项的文字格式调了一下（比如从"工号 | 姓名"
  改成"姓名（工号）"），删除或者编辑就删错人。
- **原因**：程序去拆界面上的字符串来还原数据。显示文本属于展示层，随时会变。
- **处理**：把整条记录塞进列表项的自定义槽位：
  `item->setData(Qt::UserRole, QVariant::fromValue(employee));`，
  取的时候 `current->data(Qt::UserRole).value<Employee>()`。
- **预防**：**界面文本和业务数据永远分开存**。主键必须单独存一份。

### 2.5 状态区越用越长 / 状态被日志冲掉

- **现象**：员工数量每次刷新都追加一行，日志越滚越长；或者刚写的状态转眼被覆盖。
- **原因**：把两件不同的事塞进了一个标签。"事件"应该追加（发生了就留痕），
  "状态值"应该覆盖（只关心现在是多少）。
- **处理**：拆成两个控件：`appendStatusText()` 只给事件用，
  `setEmployeeCount()` 这类用 `setText` 覆盖。
- **预防**：动手写之前先问一句——这个信息是"发生过一件事"还是"现在是多少"。

### 2.6 严重错误的提示被后来的普通状态顶掉

- **现象**：模型文件缺失时状态栏先显示"模型加载失败"，一秒后被"服务器连接失败"
  覆盖，于是你跑去查网络，方向完全错了。
- **原因**：多个模块共用一个状态标签，谁后写谁生效，没有优先级概念。
- **处理**：把"致命且不会被修复"的问题放在优先级最高的位置，后续次要状态
  不再覆盖它。
- **预防**：一个标签承担超过两种含义的时候，就该拆了。

## 三、摄像头与图像

### 3.1 画面左右反了（我左偏头，画面里往右偏）

- **现象**：前置摄像头预览像照镜子。
- **原因**：摄像头输出的是"别人看你"的视角，前置摄像头需要水平翻转才符合直觉。
- **处理**：`cv::flip(frame, frame, 1);`，第三个参数 1 表示水平翻转。
- **预防**：这是**显示层**的问题，别去改识别逻辑；识别对镜像不敏感。

### 3.2 画面颜色不对（人脸发蓝）

- **现象**：预览整体偏蓝或者红蓝互换。
- **原因**：OpenCV 的 `cv::Mat` 默认是 BGR 顺序，Qt 的 `QImage` 要 RGB。
- **处理**：从 `cv::Mat` 转 `QImage` 时用 `QImage::Format_RGB888` 并做通道交换
  （`cv::cvtColor(frame, rgb, cv::COLOR_BGR2RGB)`）。
- **预防**：颜色不对先怀疑通道顺序，不要怀疑摄像头坏。

### 3.3 摄像头打不开

- **现象**：点"打开摄像头"没反应，或者报错。
- **原因**：设备被别的程序占用（QQ、钉钉、相机应用）；或者索引不是 0。
- **处理**：`camera_.open(0)` 返回 false 时要明确提示，并且不要继续往后跑。
- **预防**：打开失败的路径必须写；只测成功路径的话，演示当天一定会翻车。

### 3.4 画面掉帧、界面发卡

- **现象**：预览一顿一顿的，点按钮反应慢。
- **原因**：预览定时器大约 30 毫秒一次，如果在同一个回调里每帧都跑人脸检测，
  GUI 线程被算力占满。
- **处理**：把检测节流到大约 100 毫秒一次，预览按原频率刷新。
- **预防**：**界面刷新频率和计算频率要分开**。凡是重计算，都要问"真的需要每帧都算吗"。

### 3.5 摄像头中途失效后界面像卡死 **[推断]**

- **现象**：拔掉摄像头或者被别的程序抢走后，状态栏每秒闪几十次同样的错误，
  一直不恢复，用户不知道该点哪里。
- **原因**：读帧失败只写了一句提示就返回，定时器还在跑。一秒钟三十次，
  每次写一遍，看起来像卡死。
- **处理**：读帧失败时调用 `stopCamera()`：停定时器、释放设备、界面恢复到
  "未开启"，然后再给一句"请检查设备后重新打开"。
- **预防**：**失败路径要负责把系统带回一个稳定状态**，不能只报告不处理。
- **备注**：本机是内置摄像头，拔不掉，这条没能实测，是按逻辑改的。

### 3.6 开一次摄像头只发一帧

- **现象**：服务端收到的永远是第一帧，人走开了它还挂着上一个人的名字。
- **原因**：发送逻辑一开始为了"只发一张测试图"，用了一个发过就置位的开关
  `jpegSent_`。功能验证完忘了换成持续发送。
- **处理**：改成按时间间隔发送（500 毫秒一帧，约每秒 2 帧），
  并且**去掉"客户端先检测到脸才发"的条件**。
- **预防**：客户端检测能力比服务端弱的时候，不要拿它当"要不要发"的闸门；
  而且没有"没人脸"的帧，服务端永远不知道人已经走了。

## 四、人脸检测与识别

### 4.1 以为必须自己编译 opencv_contrib

- **现象**：想用 LBPH 做人脸识别，查资料说要编译 opencv_contrib，于是准备花几个小时。
- **原因**：OpenCV 官方 Windows 包确实不带 contrib 里的 `face` 模块（没有 LBPH）。
  但**人脸识别不是只有 LBPH 一条路**。
- **处理**：`cv::FaceDetectorYN` 和 `cv::FaceRecognizerSF` 在主仓库的
  `objdetect` 模块里，官方包已经带了。用 YuNet 检测 + SFace 提特征，一行都不用编译。
- **预防**：换方案之前先查清楚"这个东西到底在哪个模块"，别听经验之谈就动手编译。

### 4.2 模型文件不见了，程序直接崩（连窗口都没有）

- **现象**：删掉或者改名模型文件后启动，弹出 `Debug Error! abort() has been called`，
  窗口根本不出现。
- **原因**：`FaceDetectorYN::create()` / `FaceRecognizerSF::create()` 在文件读不到时
  **抛异常**，而不是返回空指针。异常没人接，穿出 `main()` 就调用 `std::terminate`。
  原来只写了检查空指针的代码，等于白写。
- **处理**：两次 `create` 各包一层 `try/catch (const cv::Exception&)`，
  **同时保留 `empty()` 检查**——异常和空指针是两条不同的出错路径，两条都要防。
- **预防**：用任何新 API 之前，先确认它的错误处理方式是"返回错误码"还是"抛异常"。
  同一个库内部都可能不统一。

### 4.3 客户端用 Haar、服务端用 YuNet，两边结论打架

- **现象**：客户端明明给脸画了绿框，服务端却说"未检测到人脸"。
- **原因**：两套检测器精度不同。Haar 只认正脸，稍微歪头就漏检。
- **处理**：客户端也换成 YuNet，两边用同一个阈值。
- **预防**：**同一个判定不能在两个地方用两套标准**，否则用户看到的是自相矛盾的界面。

### 4.4 头一歪就检测不到人

- **现象**：正对镜头没问题，头偏十几度脸就"消失"了。
- **原因**：YuNet 的检测置信度阈值默认是 **0.9**，意味着"九成把握才敢说这是脸"。
  人脸偏转之后置信度掉到 0.9 以下，整行结果被丢弃。
- **处理**：降到 0.7。实测同一张偏转 15 度的图，0.9 时完全找不到，0.7 时能正常
  检测并算出特征。
- **预防**：要分清项目里的**两个阈值**（见下一条），别调错了那个。

### 4.5 分不清"两个阈值"，调错地方

- **现象**：识别率不对，不知道该调哪个数。
- **原因**：项目里有两个独立的阈值，管的是完全不同的两件事：

  | 阈值 | 作用 | 调高的后果 | 调低的后果 |
  | --- | --- | --- | --- |
  | 检测 0.7 | 多确定算"这是脸" | 漏检，歪头就找不到人 | 误检，把不是脸的框进来 |
  | 识别 0.363 | 多像算"是同一个人" | 别人也能刷进你的账号 | 本人也经常认不出来 |

- **处理**：脸上找不到框 → 调检测阈值；框住了但认不出 → 调识别阈值。
- **预防**：这两个数是**模型自带的参数**，不是业务规则，应该放在模型那一层，
  不要散落在业务代码里。

### 4.6 从 Haar 换成 YuNet 之后检测出错或结果很怪

- **现象**：换了检测器，结果不对甚至报错。
- **原因**：Haar 吃灰度图，YuNet 是神经网络，**只吃彩色图**。原来的代码里有一句
  "先转成灰度"，换检测器时最容易漏掉这一步。
- **处理**：去掉转灰度，直接把彩色帧传进去。
- **预防**：换掉某个组件时，列一张"输入输出约定"的清单对着改，别只改类型。

### 4.7 多人入镜时认错人

- **现象**：画面里有两个人，结果取的是不可预测的那个。
- **原因**：代码取了检测结果的第一行，但**官方文档只说明输出是 N 行 15 列的矩阵，
  没有承诺按什么顺序排**。
- **处理**：自己按置信度挑最高分的那张脸，不要依赖未写进文档的行为。
- **预防**：只要文档没写，就当它随时会变。

### 4.8 日志又刷屏了：去重键用错了

- **现象**：明明加了"只在结果变化时记一行"，真机上还是每秒刷两行。
- **原因**：去重键用的是**显示文字**，而那行文字里带着相似度（比如 0.0493）。
  摄像头每一帧都在轻微变化，相似度会不停抖动，文字跟着变，于是每帧都被
  当成"新状态"。用固定图片测试时看不出来，因为图片一模一样。
- **处理**：去重改成比"状态"——有没有脸、认出来没有、认出来的是谁，
  相似度继续显示但不参与判断。
- **预防**：**去重要去在语义状态上，不能去在展示文字上**。

### 4.9 同一张脸被登记给了两个员工

- **现象**：把一个人的人脸登记给 A，又登记给 B，两次都提示成功。
- **原因**：登记流程只检查"这个员工有没有模板"，没有检查"这张脸有没有别人在用"。
- **处理**：登记前拿新脸跟**除自己以外**的所有模板比一遍，只要有超过识别阈值
  （0.363）的就拒绝，并告诉用户像谁。本人重新登记要放行，因为那是正常的覆盖更新。
- **预防**：凡是"唯一"的业务约束，都要问一句"两个不同的发起方同时做会怎样"。
  这个 bug 的后果很重：考勤会记到错的人头上，而且两条记录看起来都完全正常。

### 4.10 特征向量存进数据库后，读出来不对

- **现象**：模板存了、也读回来了，但比对结果乱七八糟。
- **原因**：有两个坑。一是长度没校验，数据库里的脏数据会让 `memcpy` 越界；
  二是 `cv::Mat` 的赋值是**浅拷贝**，`lastEmbedding_ = embedding` 只是两个名字
  指向同一块内存，那块内存下一帧就被复用了。
- **处理**：存的时候按字节整块取（`1x128` 的 float 正好 512 字节），
  取的时候校验长度；长期保存的特征一定要 `clone()`。
- **预防**：`cv::Mat` 不是值类型，把它当成"智能指针 + 长度"来理解。
  实测同一张图存取往返的相似度是 1.0000，说明序列化本身是无损的。

## 五、网络与协议

### 5.1 消息发一次收两次、或者收到半条

- **现象**：发两条短消息，服务端当成一条；或者发一张大图，服务端只收到一半。
- **原因**：TCP 是**字节流**，没有消息边界。你写两次，对面可能一次读到；
  你写一次，对面可能分三次读到。这叫粘包和半包，是常态不是异常。
- **处理**：自己定协议：4 字节大端长度 + 内容。接收端缓冲，够一帧才切出来。
- **预防**：**"半条到了"和"两条粘一起"一定要写测试**，这两个场景在真实网络里
  每天都会发生。

### 5.2 切帧函数返回真/假，调用方没法正确反应

- **现象**：写完整性检查时发现，真和假都不够用。
- **原因**：这里其实有三种情况：数据没到齐（继续等）、切出一整帧（交给上层）、
  长度字段明显不对（流已经错位）。前两种都返回假，调用方区分不出来。
- **处理**：返回枚举 `Complete / Incomplete / Invalid`。
- **预防**：**返回值含义超过两种的时候，用枚举，别硬塞进 bool。**

### 5.3 端口被占用：The bound address is already in use

- **现象**：服务端一启动就报端口被占用。
- **原因**：`server.listen()` 被调用了两次，第二次必然失败。更糟的是第二次调用写在
  判断之外，把"数据库不可用就不启动"这条策略也绕过去了。
- **处理**：删掉多余的那次调用。
- **预防**：同一个资源只初始化一次；写完"启动流程"后对着代码数一遍调用次数。

### 5.4 服务端给客户端回消息，回错了人 / 回不出去

- **现象**：想回传识别结果，发现服务端只会收不会发；或者两个客户端同名分不清。
- **原因**：服务端原来的结构只处理"收到消息"，没有发送路径；而且客户端标识
  只用了 IP，同一台机器开两个客户端就重名。
- **处理**：`ClientConnection` 加 `sendPayload()`，`Server` 加 `sendToPeer()`；
  客户端标识带上端口号（`IP:端口`）。
- **预防**：设计协议的时候**一开始就想清楚是不是双向的**，别等要用了才补。

### 5.5 服务端没开，客户端必须重启

- **现象**：先开客户端再开服务端，客户端永远连不上，只能重启客户端。
- **原因**：连接失败之后没有任何重试。
- **处理**：客户端记住地址，断线后每 3 秒重连一次；重连前先 `abort()`
  把上一次的残留状态丢掉；连上之后停掉定时器。
- **预防**：凡是网络程序，**默认就要考虑"对面还没起来"和"对面重启了"**。

### 5.6 收到畸形数据后连接还挂着

- **现象**：给服务端发一个长度字段是 40 亿字节的包，服务端只清了缓冲，连接没断。
- **原因**：长度字段错误意味着这条字节流已经错位，**后面再也对不齐了**，
  清掉缓冲继续读只是撞运气，而且畸形数据会一直占着资源。
- **处理**：检测到不可能的长度直接断开这条连接。
- **预防**：分清"可以恢复的错误"和"流已经废了"。后者要立刻终止，不要试图打捞。

### 5.7 分帧代码写了两份

- **现象**：服务端和客户端各有一份切帧逻辑，改协议要改两个地方，还容易只改一边。
- **原因**：两份都是私有方法，藏在各自的网络类里，没法共用也没法单独测。
- **处理**：挪到 `common/FrameProtocol::takeFrame()`，两边都调它。
- **预防**：**协议规则属于双方共用的东西，一开始就该放在公共层**，
  而且它应该是"吃字节、吐字节"的纯函数，这样才能毫秒级单测。

## 六、数据库与考勤

### 6.1 用户看到的是数据库原文

- **现象**：工号重复时，界面直接显示
  `UNIQUE constraint failed: employees.employee_no Unable to fetch row`。
- **原因**：数据库错误分两类，代码没区分：**可预期的业务错误**（工号重复、必填为空）
  和**不可预期的系统错误**（磁盘满、库损坏）。前者用户自己能解决，应该给人话。
- **处理**：插入之前先按工号查一次，查到就提示"工号 xx 已存在"。
- **预防**：**唯一约束仍然要保留**。查重和写入之间有间隙，两个人同时插入时
  只有约束拦得住。两道防线各管一件事：约束保正确性，前置检查保体验。

### 6.2 删了员工，他的考勤记录还留着

- **现象**：删掉员工后，考勤表里出现指向不存在员工的数据。
- **原因**：外键写了 `ON DELETE CASCADE`，但 SQLite 默认**不打开外键约束**，
  必须每次连接都执行 `PRAGMA foreign_keys = ON`。
- **处理**：在初始化 schema 的时候执行这个 PRAGMA。
- **预防**：换数据库（尤其是从 SQLite 换到 MySQL）之后，这类"默认行为不同"的
  地方要重新确认一遍。

### 6.3 限流时间差了 8 小时

- **现象**：限流要么永远命中、要么永远不命中。
- **原因**：`created_at` 由 SQLite 的 `CURRENT_TIMESTAMP` 写入，值是 **UTC**；
  如果用 Qt 的本地时间去比，在东八区会差 8 小时。
- **处理**：时间比较整个交给数据库做：`created_at > datetime('now', '-120 seconds')`，
  两边都是 UTC，基准只有一个。
- **预防**：**跨系统比时间，永远先问"这个时间是什么时区"**，再动手写比较。

### 6.4 限流写成了永久生效

- **现象**：同一个人被记过一次之后，当天再也记不上。
- **原因**：判断写成了"这个人有没有记录过"，而不是"最近两分钟内有没有记录过"。
- **处理**：改成按时间窗口过滤，并**写一个测试**：手工插一条两小时前的记录，
  确认它不算在 120 秒窗口里。
- **预防**：凡是带"最近 N 分钟"的规则，都要有一个"超出窗口就不算"的测试。

### 6.5 工号被改了

- **现象**：编辑员工时把工号也改掉了，历史考勤跟人对不上。
- **原因**：工号是**业务主键**，现实里入职分配之后是固定的。
- **处理**：更新函数的签名里**压根不给工号这个参数**，调用方想改也改不了；
  界面上选中员工后把工号框设为只读。
- **预防**：**把约束放进签名，比写在注释里可靠。** 注释只能提醒人，签名能拦住人。

### 6.6 数据库打不开时服务端照样起来了

- **现象**：界面上写着"数据库不可用，服务器未启动"，其实端口已经在监听。
- **原因**：启动检查的 `else` 分支写得没问题，但后面还有一句无条件的
  `server.listen()`，把判断绕过去了。
- **处理**：把启动条件串成 `if / else if / else`，数据库和模型任一不可用就不监听。
- **预防**：启动流程里的"前置条件"要串成一条链，不能有漏在判断之外的语句。

## 七、构建、测试与部署

### 7.1 改了 CMakeLists 还是改了源码，什么时候要重新配置

- **现象**：加了一个新文件，编译报"找不到符号"。
- **原因**：新文件没有加进 `CMakeLists.txt` 的源文件列表。
- **处理**：把文件加进目标；CMake 会自动重新配置。
- **预防**：**加文件 = 改 CMakeLists**。只改已有文件的内容不需要重新配置，
  加删文件一定要。

### 7.2 数据库测试一跑就崩

- **现象**：协议测试正常，数据库测试直接段错误，位置在 `addDatabase` 附近。
- **原因**：Qt 的 SQL 模块需要有一个 `QCoreApplication` 实例才能加载驱动，
  而 `QTEST_APPLESS_MAIN` 什么都不创建。
- **处理**：改用 `QTEST_GUILESS_MAIN`（创建一个没有界面的应用实例）。
- **预防**：用到 SQL、网络、文件监听的测试，都不能用 APPLESS。

### 7.3 测试程序找不到 Qt 的 DLL

- **现象**：ctest 报"找不到 Qt6Core.dll"。
- **原因**：测试 exe 的输出目录和主程序不一样，那里没有部署 Qt 的 DLL。
- **处理**：让测试和主程序输出到同一个目录，或者用 POST_BUILD 把
  `$<TARGET_FILE:Qt6::Core>` 之类复制过去。
- **预防**：**插件**（比如 SQLite 驱动）不用手动复制，Qt 会按安装目录自己找；
  但换到没装 Qt 的机器上就必须靠 `windeployqt` 收齐，见下一条。

### 7.4 打包给别人运行时缺 DLL（待做）

- **现象**：把 exe 拷到别的电脑上双击，报缺少各种 DLL。
- **原因**：Qt 和 OpenCV 都是动态链接，运行时依赖一大堆 DLL 和插件。
- **处理**：用 Release 配置构建，然后对每个 exe 跑 `windeployqt`，
  确认 `platforms/`、`sqldrivers/` 这些插件目录都在。
- **预防**：打包完**在一台没装过 Qt 的机器上试**，别在本机试，本机一定会成功
  因为有环境变量兜底。

### 7.5 客户端的 models 目录越堆越多

- **现象**：换了几次模型之后，`models/` 里躺着一堆用不到的文件。
- **原因**：CMake 的 `copy_if_different` 只负责"该有的有"，不负责"不该有的删掉"。
- **处理**：定期清理；退役的模型和死代码一起删。
- **预防**：换模型的时候顺手看一眼那个目录。

### 7.6 大文件要不要提交进仓库

- **现象**：SFace 模型 37 MB，提交之后仓库永久变大。
- **原因**：Git 保存每次提交的完整内容，删掉也不会让仓库变小。
- **处理**：这个项目选择提交，理由是"clone 下来就能跑"比体积重要。
- **预防**：如果要省体积，就把模型加进 `.gitignore`，在 README 里写清楚
  下载地址和许可证。

## 八、还没验证或还没做的

这几条是已知但没完成的，复现项目时留意：

1. **摄像头中途失效的恢复路径**：本机是内置摄像头拔不掉，只按逻辑改了，没实测。
2. **长度合法但内容只发一半的包**：服务端会一直等，没有超时。修法是加超时断开。
3. **库里已经存在的重复人脸模板**：新登记会被拦住，但历史数据需要人工清理
   （删掉其中一个员工再重建，或者做一个"取消人脸登记"的功能）。
4. **接口测试**：现在只测了协议和数据库，识别流程本身还是手工验证的。
5. **Release 打包**：见 7.4。

## 九、面试可以直接讲的几个点

如果面试官问"你遇到过什么问题、怎么解决的"，下面这几个最有含金量：

1. **粘包和半包**：TCP 是字节流，我用长度前缀自己分帧，并且把"半条"和"粘包"
   写成了单元测试。
2. **模型加载会抛异常**：不是返回空指针，没接住会 `abort`。我最后是
   try/catch 和空指针检查两道都做了。
3. **日志去重的键不能是显示文字**：相似度每帧都抖，拿文字当键等于没去重。
   改成按"是谁"去重才有效。
4. **同一张脸登记给了两个人**：这是数据完整性问题，考勤会记到错的人头上，
   而且事后看不出来。我在登记前加了跨员工的比对。
5. **两个阈值的区别**：检测阈值管"是不是脸"，识别阈值管"是不是同一个人"，
   调高调低影响的失败类型完全不同。
6. **时区**：数据库存的是 UTC，用本地时间去比会差 8 小时，所以我把时间比较
   整个放进了 SQL。
7. **约束要放进签名**：工号不能被更新，我没有写注释提醒，而是让更新函数
   根本没有工号这个参数。
